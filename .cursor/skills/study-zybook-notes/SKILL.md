# zybook-assist

## 核心原则：架构师视角

- **不要**：在**总结模式**下逐词翻译、逐句总结、堆砌定义。
- **要**：过滤语言噪声，直击逻辑本质；优先从**系统设计**的**权衡取舍**来讲解（例如：AVL 与红黑树在海量读写场景下的性能差异、适用场景）。
- **价值**：便于面试与架构师视角积累素材。

示例：学到 AVL 树时，输出应包含「与红黑树的对比 + 典型使用场景」，而非仅定义与性质罗列。输出还应包含**算法间的优劣对比 + 每种算法的使用场景**（如：选择排序仅用于教学、生产级已淘汰；归并排序用于大规模数据排序；快速排序用于内存内高效排序）。

- **总结模式**：用户提出“总结/复习/术语表/强化练习/章节提炼”等需求时使用，遵循下文“五步工作流”。
- **翻译模式**：用户提出“翻译/translate/译成某语言”等需求时使用，遵循下文“翻译模式工作流”。
- **冲突处理**：若同一请求同时包含总结与翻译，先完成用户明确优先的任务；未说明优先级时，先翻译再按翻译结果做总结。

## 输出与落盘（Markdown 文件保存）- 必须遵守

### 语言规则（默认中文）

- **总结模式**：默认中文输出。
- **翻译模式**：将文档翻译成用户指定语言；若未提及目标语言，默认翻译成中文。
- 仅当用户明确要求英文时，整篇切为英文（包括小节标题与术语表列名）。英文触发信号包括但不限于：
  - `请以英文总结` / `英文总结`
  - `en:` / `EN:`
  - `请用英文`

### 伪代码语言规则（必须遵守）

- 伪代码主体必须使用英文：关键字、流程控制、函数名、变量名统一英文（如 `if`、`for`、`while`、`return`）。
- 中文输出时：伪代码注释使用中文。
- 英文输出时：伪代码注释使用英文。
- 不因正文语言变化而切换伪代码关键字语言；仅注释语言随输出语言切换。

### 图示增强（可视化优先，用于提升笔记可读性）

当生成学习笔记（尤其是**总结模式**）时，如果图示能显著提升理解与复盘效率，必须配图（draw.io SVG），并以**引用**方式插入 Markdown，避免把整段 SVG 代码内嵌到正文导致可读性下降。

**优先配图的内容类型（典型信号）：**
- 图论：节点/边/权重表、遍历路径、最短路、最小生成树
- 树与索引结构：BST、AVL、红黑树、堆、递归树、旋转/重平衡过程
- 动态规划：状态定义、转移关系、表格填充顺序、依赖 DAG
- 算法流程：排序/搜索/递归/分治/回溯/图遍历的关键步骤与分支
- 系统流程：缓存/索引/队列/请求流/数据结构操作流水线

**强制工具与格式：**
- 最终落盘图示（即保存到 `images/` 并插入文档的图）必须使用 `transform-markdown-svg`（draw.io/diagrams.net 导出 SVG），不得用 Mermaid 替代。
- Mermaid 仅允许作为 **临时文本草图** 用于分析中辅助理解（如快速画个概念关系），但 **不得保存为最终图示产物**，不得嵌入 `images/` 目录，不得替代 `transform-markdown-svg` 的 draw.io SVG。
- 图示输出位置：目标笔记 Markdown 同级 `images/` 目录（由 `transform-markdown-svg` 统一管理）。
- Markdown 插入格式默认使用 Obsidian 引用：`![[images/<name>.svg]]`（不要内嵌 `<svg ...>`）。

**信息不足时的策略：**
- 不要强行画图；先给出保守文字总结，并向用户索要必要细节（如节点/边列表、权重表、状态转移表/公式、关键分支条件）。

### 保存目录规则（用户指定优先）

将输出内容（总结或翻译）以 **Markdown 文件**保存到以下目录（按优先级）：

1. **用户显式指定的目录**：若用户在指令中提供 `@某个目录/`（或给出明确的目录路径），保存到该目录。
2. **当前选择的目录**：若用户未指定目录，但 IDE 上下文能提供“文件树中当前选中的目录”，则保存到该目录。
3. **当前文件所在目录**：若未指定目录且无可用的“当前选择目录”，则保存到“当前正在处理/聚焦文件”的所在目录。
4. **工作区根目录**：若无法推断当前选择目录/当前文件路径，退化保存到工作区根目录。

### 文件命名规则（标题优先；无标题则主题）

每次任务 **新建一个文件**（不覆盖旧文件）。文件名规则：

1. **优先取标题**：从输入内容中提取标题作为文件名主体：
   - 首选：输入 Markdown 的第一个一级标题 `# 标题`。
   - 备选：用户显式提供的章节名/主题名（如 `第 8.2 节 ...`、`第 ... 章`、课程讲义标题等）。
2. **没有标题则自动生成主题**：对输入内容做一句话主题提炼，生成一个短主题作为文件名主体（中文优先中文；英文优先英文）。
3. **无日期前缀**：文件名不包含时间戳，仅用标题或主题。
4. **使用下划线**：最终文件名为 `<标题或主题>.md`，其中：
   - 空格、连字符 `-` 等替换为下划线 `_`
   - 示例：`bucket_sort_and_radix_sort.md`、`avl_tree.md`
5. **文件名清洗**：
   - 移除或替换非法字符：`/ \\ : * ? " < > |`
   - 合并连续空白为单个 `_`
   - 限制长度（建议 ≤ 80 字符；超长截断）

## 总结模式：五步工作流

收到 zyBooks 章节内容（或 OCR 得到的伪代码/图示说明）后，按以下五步输出。

### 第 1 步：逻辑与权衡提炼

- 必须**显式写出或画出本章核心知识点之间的关联**（如：A 是 B 的一种实现，C 是 B 的优化/特例）。可用简短层级列表、关系句或 Mermaid 图，放在第一节「一、知识点关系」中。
- 如果“知识点关系”用图更清晰（例如：依赖关系、从属/实现/优化关系、模块交互），则调用 `transform-markdown-svg` 生成一张 draw.io SVG，并在「一、知识点关系」中用引用方式插入：`![[images/<topic>.svg]]`。
- 提炼本章在系统设计中的核心思想、数据结构/算法选择带来的权衡、典型应用场景（如大规模读写、缓存、索引等）。用要点或短段，不堆砌定义。
- 必须**提供本章所涉算法/数据结构之间的比对**：从优劣（时间/空间、实现难度、常数因子、最坏/平均等）角度简要对比。
- 必须**说明每种算法/方案的使用场景**：明确「何时用、何时不用」，可参考表述如：仅用于教学、生产级已淘汰、大规模数据排序、内存内高效排序、对最坏延迟有要求的系统等。

### 第 2 步：算法模块（基于图片附件）

- 在「三、算法」中输出：算法核心流程、关键步骤（或伪代码逻辑）、时间/空间复杂度、边界条件。
- 若输出伪代码，必须遵守“代码英文、注释随输出语言切换（中文输出注释中文；英文输出注释英文）”规则。
- 算法模块内容**优先从用户提供的图片附件**中提取（算法图示、流程图、伪代码截图等）。
- 若用户未提供可用图片附件，需先明确提示用户补充算法相关图片，再基于现有文本给出保守分析，并标注待补充信息点。
- 如果算法/数据结构的“状态变化”或“流程分支”用图更清晰（如：树旋转、DP 表格填充、图遍历队列变化），则调用 `transform-markdown-svg` 生成图示并在「三、算法」对应位置插入引用：`![[images/<topic>.svg]]`。

### 算法渲染规范来源（必须遵守）

- 本 skill 的算法章节渲染由原子 skill `transform-algo-render` 统一定义。
- 在生成「三、算法」时，必须遵循该原子 skill 的完整输出契约：

  - `.pseudocode` 渲染块（`<style> + <div class="pseudocode">`）

- 语言策略沿用原子 skill：代码英文；注释随正文语言切换。

### 第 3 步：本章核心术语表

按四列输出：**术语 | 计算机科学定义 | 直观类比 | 典型应用场景**。只收「本章核心」术语，不穷举生词。**术语列格式**：采用「中文（英文原词）」——翻译或中文名称后，括号内保留英文原词；默认中文输出时以「中文（英文原词）」为准。便于每日 30 分钟复盘时只看此表，把单词学习与知识点强绑定。

### 第 4 步：执行前信息补全（不写入文章）

- 若算法模块所需材料不足（尤其缺少图片附件中的图示/伪代码），先向用户提问补全信息，再继续生成最终输出。
- 该提问属于执行前交互，**不作为文章章节输出**，不要写入最终 Markdown 文档。

### 第 5 步：强化练习（放在最后）

## 示例

**输入**（zyBooks 风格短文）：

> AVL 树是一种自平衡二叉搜索树，任一节点左右子树高度差最多为 1。插入或删除后，通过左旋、右旋或双旋恢复平衡。

**输出**（缩略版）：

**一、知识点关系**
- AVL 树（AVL tree）是自平衡二叉搜索树的一种实现；旋转（rotation）是 AVL 维持平衡的具体操作。

**二、逻辑与权衡**
- 核心思想：用严格平衡（左右子树高度差 ≤1）保证查找 O(log n)，适合读多写少。
- 算法比对（优劣）：与红黑树相比，AVL 查找更快、插入/删除代价更高（旋转更频繁）；红黑树常数更小、写操作更少。
- 使用场景：AVL 适合读多写少、需要稳定查找延迟的索引或缓存；红黑树适合海量读写、生产级通用平衡树（如 `std::map`）；仅教学演示时可用简单二叉搜索树。

**三、算法**
- 关键流程：按序插入节点后，自底向上检查平衡因子；遇到最小失衡子树时执行 LL/RR/LR/RL 旋转并停止向上扩散调整。
- **Running Time / 时间复杂度：** $O(\log n)$（单次插入平均/最坏）。
- **Reasoning / 复杂度说明：**
  - 从新节点到根的回溯路径长度为树高，AVL 树高为 $O(\log n)$。
  - 每层检查平衡因子为 $O(1)$，且单次插入最多触发常数次旋转。
  - 删除场景可能出现多次向上再平衡，仍受树高上界约束。
- 伪代码示例（中文输出，遵循 `transform-algo-render` 模板）：
  ```text
  **Algorithm** rebalanceAfterInsert(path)
    - **Input:** path from inserted node to root
    - **Output:** root of rebalanced subtree
    - **for** each node in path **do** // 自底向上检查平衡因子
    -   **if** isUnbalanced(node) **then**
    -     **return** rotate(node) // 返回调整后的子树根
    - **return** path[0]
  ```

**四、本章核心术语表**
| 术语 | 计算机科学定义 | 直观类比 | 典型应用场景 |
|------|----------------|----------|--------------|
| AVL 树（AVL tree） | 左右子树高度差不超过 1 的自平衡二叉搜索树 | 严格平衡的天平，稍微加码就要调平 | 读多写少的索引、需要稳定查找延迟的场景 |
| 旋转（rotation） | 通过局部子树重组恢复平衡的操作 | 拧一下天平支点，让两边重新平衡 | 插入/删除后的再平衡 |

**五、强化练习（示例 1 题）**
- **题型**：给定插入序列，画出 AVL 并标出每次旋转类型。
- 解题套路：按序插入 → 每次插入后从新节点向上找第一个失衡节点 → 根据「左左/右右/左右/右左」选单旋或双旋 → 只调整最小失衡子树。

## Findings

1. **Blocking — the sequential commit-chain invariant rejects the required
   A/B/C flow.** In `.ai/workflows/scripts/workflow_runtime/state.py:781-835`,
   an active slice must have a `base_ref` equal to every completed dependency's
   `accepted_head_ref`, and differing dependency heads are classified as
   `commit_chain_unsatisfiable`. On one sequential branch, independent A then B
   naturally produce different accepted heads, while C starts from the latest
   accepted sequential head (B), with A already an ancestor. The implementation
   therefore rejects the plan/spec's required A/B/C scenario instead of
   validating the single contiguous branch chain.

2. **Blocking — Git range validation is skipped in real Git worktrees.**
   `.ai/workflows/scripts/workflow_runtime/dispatch.py:768-771` treats a checkout
   as Git-backed only when `<root>/.git` is a directory. In linked worktrees,
   `.git` is a file, so `_validate_git_refs` returns success without checking ref
   existence, ancestry, or range. This contradicts the required worktree-mode
   contract.

3. **Blocking — `commit_refs` range equality and ordering are not validated.**
   `.ai/workflows/scripts/workflow_runtime/dispatch.py:800-839` only verifies that
   each supplied ref lies somewhere between base and head. A partial list such
   as `[head]` passes even when `base..head` contains intermediate commits; a
   reordered list also passes. The documented ordered, contiguous range contract
   remains unenforced, and the focused tests do not exercise omissions or order.

4. **Blocking — canonical bootstrap templates are stale.** Fresh command
   `python3 skills/sdlc-project-bootstrap/scripts/sync_templates.py --root . --check`
   exited non-zero and reported drift for live `state.py` and `dispatch.py`.
   The canonical templates omit the recovered Git validation, aggregate-review,

## Issues

- The tests model symbolic refs in non-Git fixtures, which allows the required
  A/B/C scenario test to stop before state validation exposes the invalid
  dependency-head invariant.
- The Git tests initialize only a normal checkout and assert membership, not
  exact ordered equality with `git rev-list --reverse base..head`.
- Recovered implementation evidence describes the final remediation narrowly,
  while the live worktree contains the full P0 implementation. The structured
  changed-file evidence covers the broad directories, so this was reviewed as
  the recovered aggregate live change set rather than rejected as missing.

## Learnings

- Dependency readiness and sequential Git ancestry are separate invariants:
  dependency heads need to be ancestors of the current base, while the current
  base must equal the latest accepted sequential head.
- Detecting `.git` by directory shape is not worktree-safe; Git itself must be
  queried to determine repository validity.
- Per-element range membership is weaker than exact ordered range equality.
- A green full suite does not compensate for behavior tests that encode the
  wrong commit-chain model or omit worktree and exact-range cases.

## Suggestions

- Add a real temporary-repository A/B/C integration test where B starts from
  A's accepted head and C starts from B's accepted head while depending on both.
- Add a linked-worktree test and exact ordered `commit_refs` comparison against
  `git rev-list --reverse <base>..<head>`.
- Make template sync part of the implement-agent's structured verification
  commands so recovered evidence includes the exact command and result.

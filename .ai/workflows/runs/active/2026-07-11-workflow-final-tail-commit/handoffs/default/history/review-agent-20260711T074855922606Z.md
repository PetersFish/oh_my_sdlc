## Issues

### Blocking: final-commit can commit unrelated pre-staged files

`cmd_final_commit` stages each allowlisted dirty path, but then obtains `staged_paths` from the repository-wide `git diff --cached --name-only` and runs an unrestricted `git commit -m ...`. Any unrelated file that was already staged before the command runs is therefore included in the final commit. This violates the spec requirements to stage/commit only allowlisted governance artifacts and never commit allowlist-external dirty files.

The current unrelated-file test covers only an untracked/unstaged file, so it remains green for this broken case.

Required remediation:

1. Ensure the commit cannot include pre-existing staged paths outside the allowlist while preserving the caller's index state.
2. Add an executable regression test that pre-stages an unrelated tracked file, runs `final-commit`, proves the unrelated file is absent from the resulting commit, and verifies its prior staged state is preserved (or otherwise follows an explicitly approved index-state contract).
3. Re-run focused runtime tests and the relevant regression/sync checks.

## Learnings

- A dirty-path allowlist is insufficient when Git's index may already contain staged changes; commit scope must be constrained independently of staging newly allowed paths.
- Behavioral coverage must include both unstaged and pre-staged unrelated files because `git commit` consumes the index, not only paths staged by the current command.

## Suggestions

- Add index-state scenarios to the final-commit test matrix: unrelated staged changes, mixed staged/unstaged changes on one path, and commit failure with index preservation.
- Include the pre-existing-index policy explicitly in the final-commit spec so command behavior is deterministic for non-clean developer worktrees.

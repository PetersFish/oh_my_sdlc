## Objective

Implement required behavior and coverage for four review blockers in the SDLC workflow runtime's sliced apply-change P0 implementation:

1. Aggregate review rejected by before-dispatch as `unknown_slice`
2. Commit-chain invariant unsatisfiable for slices with multiple differing dependency heads
3. Sliced implement dispatch can proceed without a `slice_id`
4. Git range validation checks only non-empty strings rather than ref existence, ancestry, contiguity, and range equality

## Work Completed

### Blocker 1: Aggregate Review `unknown_slice` Fix

**File**: `.ai/workflows/scripts/workflow_runtime/dispatch.py`

Added a short-circuit in `cmd_before_dispatch` that handles `slice_id == "aggregate"` for `review-agent` before the unknown_slice lookup. When `slice_id` is `"aggregate"`:
- If `aggregate_review_status` is `"ready"`, dispatch is allowed.
- If `aggregate_review_status` is not `"ready"`, a new `aggregate_review_not_ready` blocker is emitted instead of `unknown_slice`.

### Blocker 2: Commit-Chain Unsatisfiable Multi-Dep Detection

**File**: `.ai/workflows/scripts/workflow_runtime/state.py`

Extended `validate_implementation_state` to detect the unsatisfiable case where a slice depends on two or more completed slices with differing `accepted_head_ref` values. When detected, a `commit_chain_unsatisfiable` error is emitted with all differing ref values. The per-dependency `commit_chain_violation` check is skipped for that slice (the unsatisfiable error covers it).

### Blocker 3: Missing `slice_id` for Implement Dispatch

**File**: `.ai/workflows/scripts/workflow_runtime/dispatch.py`

When `implement-agent` is dispatched without `--slice-id` and implementation state has explicit multi-slice state (more than one slice or a non-`default` slice), a new `missing_slice_id` blocker is emitted. Single-`default`-slice (legacy/single-slice) remains allowed without `--slice-id` for backward compatibility.

### Blocker 4: Git Range Validation

**File**: `.ai/workflows/scripts/workflow_runtime/dispatch.py`

Added `_validate_git_refs(root, base_ref, head_ref, commit_refs)` helper and integrated it into `cmd_after_dispatch` for `implement-agent` success. The helper validates:
- **Existence**: `base_ref` and `head_ref` resolve to real commits (`git cat-file -e`)
- **Ancestry**: `head_ref` is a descendant of `base_ref` (`git merge-base --is-ancestor`)
- **Contiguity/Range equality**: every `commit_ref` is within the `base..head` range (descendant of base, ancestor of head)

Non-git workspaces skip validation (for test fixtures). Invalid refs produce `invalid_git_ref` blockers and prevent the slice from transitioning to `in_review`.

## Learnings

- The `after-dispatch` command never exits non-zero for blocker-only cases — it sets the run to `blocked` and returns the transition JSON with `workflow_command: "workflow.py block"`. Tests must check `data["blockers"]` and slice state, not `rc`.
- Git's `--orphan` branch is the cleanest way to create a non-descendant commit for ancestry violation tests.
- The `RESERVED_SLICE_IDS` set already prevents `"aggregate"` from being used as a real slice id in `validate_implementation_state`, so the before-dispatch short-circuit is the correct place to handle it.

## Suggestions

- Consider adding a dedicated `before-dispatch` exit-code contract for blocked dispatches (currently `rc=1` for before-dispatch, `rc=0` for after-dispatch with blockers). Documenting this asymmetry would prevent test confusion.
- The git range validation could be extended to `review-agent` success (checking `accepted_head_ref` against the repo) for additional safety.

## Risks/Follow-Ups

- The git range validation only runs when a `.git` directory exists. Worktree-mode runs with separate git dirs should be verified to work correctly.
- The `commit_chain_unsatisfiable` check could be extended to detect transitive unsatisfiability (A→B→C where A and B have different heads), though the current direct-dependency check catches the common case.

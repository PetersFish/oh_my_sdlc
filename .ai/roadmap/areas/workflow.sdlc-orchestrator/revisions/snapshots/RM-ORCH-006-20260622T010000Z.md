# Goal

Replace the single `.ai/workflows/runs/current.json` file with an `active/` directory that supports multiple concurrent workflow runs, so that parallel OpenSpec changes can each have their own active run without conflict.

# Problem Context

The current runtime uses a single `current.json` file as the active run slot. `cmd_start` treats any different-subject active run as a conflict and exits. This blocks legitimate parallel task workflows:

- **Scenario**: Start a run for change A. Before change A is done, begin work on change B. `cmd_start` finds change A's run in `current.json`, detects a different subject, and reports `conflict` — blocking change B's run.
- **Result**: Only one workflow run can exist at a time. The user must serialize all SDLC tasks, even when tasks are independent.

The fix: move from a single `current.json` to an `active/<run_id>.json` directory, where each run is stored independently by `run_id`.

# Scope

## In

- Replace `.ai/workflows/runs/current.json` with `.ai/workflows/runs/active/<run_id>.json`.
- `cmd_start` creates a new active run file without conflict checks against other active runs.
- `cmd_resume` locates the matching active run by `subject_type` + `subject_id`.
- `cmd_done` / `cmd_advance` (done path): write history, then remove from `active/`.
- `cmd_status`: when no `subject_id` given, list all active runs; when specified, show single run status.
- `governance-check`: scan `active/` for `pending_hooks` and `history/` for done evidence.
- `cmd_preflight`: use `subject_id` to find or create the correct active run.
- Update tests to cover multi-run scenarios: concurrent runs, resume by subject, status with multiple active runs, done cleanup from active directory.
- Migrate: if legacy `current.json` exists on `start`, move it to `active/<run_id>.json`.
- Sync canonical templates after implementation.

## Out

- No change to `history/` format or content.
- No change to workflow phase machine or transition logic.
- No change to the governance-check finding types — only the scan scope changes (`active/` + `history/` instead of `current.json` + `history/`).
- No automatic run prioritization or scheduling — concurrency is opt-in, not orchestrated.
- No locking or merge mechanism for concurrent runs touching the same subject.

# Design Notes

## Key Decisions

- Use a directory `active/` over a namespace-prefixed file (e.g., `current-<id>.json`) because directories are easier to scan, list, and operate on with standard filesystem tools.
- `run_id` is the filename key (e.g., `active/os-opencode_change-add-foo.json`). This keeps filenames self-describing and avoids needing to parse JSON to identify a run.
- `cmd_resume` with `subject_type` + `subject_id` finds the matching run by scanning active files and matching `primary_subject`. If exactly one matches, resume it. If none, report no active run. If multiple (shouldn't happen), report ambiguity.
- `cmd_status` without subject arguments lists all active runs in a table format. With subject, shows the single run detail.
- Migration of legacy `current.json` on `cmd_start`: if `active/` is empty but `current.json` exists, move it into `active/<run_id>.json` and continue.
- `governance-check` scans `active/` for `pending_hooks` (same logic as before, just iterating a directory) and `history/` for done evidence. No lookup by `current.json` slot.

## Tradeoffs

- Scanning a directory for matching runs is slightly slower than reading a single file, but the number of active runs is small (typically 1-3).
- Losing the "exactly one active run" invariant means some commands need explicit subject disambiguation. This is already provided by `preflight`'s `subject_type`/`subject_id` parameters.
- Concurrent runs touching the same roadmap item or same file could produce merge conflicts. This is a user-level concern, not a runtime-level concern — the runtime provides isolation, not synchronization.

## Initial Approach

1. Modify `load_run_state(root, run_id=None)` and `save_run_state(root, state)` to use `active/<run_id>.json`.
2. Add `_list_active_runs(root)` helper that scans `active/` directory.
3. Update `cmd_start`: create `active/<run_id>.json` without conflict check. Add legacy migration.
4. Update `cmd_resume`: find matching run by subject or report "no active run". Support `--run-id` for direct lookup.
5. Update `cmd_done` / `cmd_advance` (done path): write history, then `os.remove` from `active/`. (This naturally fulfills RM-ORCH-004's goal.)
6. Update `cmd_status`: list all active runs, or show single if subject given.
7. Update `governance-check`: scan both `active/` and `history/` for evidence.
8. Update `cmd_preflight` and `_evaluate_subject_run_context()` to search active/.
9. Update all tests. Add concurrent-run scenarios.
10. Run full test suite and template drift check.

## Open Questions

- Should `cmd_resume` without arguments list active runs and prompt, or require explicit `--subject-type`/`--subject-id`? (Recommended: require explicit subject for scripts, list for human CLI use.)
- Should concurrent runs on the same `subject_id` be rejected (only one active run per subject)?

# Acceptance Criteria

- Two independent `cmd_start` calls with different `subject_id` each create their own `active/<run_id>.json` without conflict.
- `cmd_resume --subject-type openspec_change --subject-id <id>` finds and resumes the correct run.
- `cmd_status` without subject lists all active runs.
- `cmd_done` moves the run to `history/` and removes it from `active/`.
- `governance-check` detects `pending_hooks` from any active run and `dangling_archive` using history evidence.
- Legacy `current.json` is migrated to `active/<run_id>.json` on next `cmd_start`.
- `python3 -m pytest tests/test_workflow.py -v` passes.
- Template drift check passes.
